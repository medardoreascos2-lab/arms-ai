# RC2R: Windows-local V3 authority and offline commissioning

This boundary is observation-only. `NATIVE_SUBMIT_ENABLED` and
`AUTO_RETRY_ALLOWED` remain false. No deployment or production provisioning is
performed by the tests or build gate.

## Trust and provisioning

The ARMS backend/provisioner and NinjaTrader must use the same Windows account.
Authority is a random 32-byte HMAC key protected using DPAPI CurrentUser with
fixed domain-separation entropy `arms.native.authority.v3`. It is stored at
`%LOCALAPPDATA%\ARMS-AI\sim-native-v3\authority.dpapi`; its encoding is the ASCII
header `ARMS_DPAPI_CURRENT_USER_V3\n` followed by the DPAPI blob. Neither raw key
bytes nor their encoding are persisted or logged. The directory DACL grants
only its effective Windows user and SYSTEM. DPAPI/HMAC, not the ACL alone,
establish authentication. Same-user code is inside this Windows trust boundary.

The explicit operator command is:

```powershell
py -B -m backend.services.sim_native_authority_v3 provision
```

This is a future commissioning command, **not run during RC2R**. It reports a
SHA-256 fingerprint. Existing valid authority is reused byte-for-byte; missing
authority is never generated by a loader. Corruption fails closed. Rotation is
not implemented and requires a separately authorized migration/recovery phase.

`build_provisioned_native_sim_runtime` is the production composition API. It
loads only canonical CurrentUser authority and delegates to the existing
disabled SIM_NATIVE runtime. It accepts no alternate key or secret root. The
original explicit-key factory remains available for offline contract tests.

## Signed configuration and owner pins

The authoritative backend explicitly calls `publish_config` with its canonical
`SimNativeAccountV3`, configuration generation, approved risk version, four
distinct existing runtime directories, and explicit UTC issue/expiry bounds in
Unix microseconds. This API does not issue admissions, activations or orders.
It writes `controlled-v3-config.json` and `controlled-v3-config.sig` beside the
protected authority. JSON is a sorted, compact, UTF-8 flat string dictionary;
the signature is lowercase HMAC-SHA256 of `arms.native.configuration.v3\0`
followed by the exact JSON bytes. The schema is `ARMS_CONTROLLED_CONFIG_V3`.

Generation increases explicitly. Repeating identical content is idempotent;
reusing a generation with different content or decreasing it is rejected.
Each file is flushed and atomically renamed. The signature commits the exact
JSON generation. Readers reject inconsistent pairs and repeat the JSON read to
detect replacement during verification. An interrupted publication fails
closed and needs explicit recovery; startup does not repair it. A leftover
publisher lock also requires explicit review, never automatic deletion.

The human-approved configuration pins on the existing indicator are
`ControlledAuthorityId`, `ControlledBackendAccountId`,
`ControlledConfigurationGeneration`, `ControlledRuntimeGeneration`,
`ControlledStateDirectory`, and `ControlledReconciliationDirectory`, together
with existing `SelectedAccountName`, `InstrumentName`, `CommandDirectory` and
`ActivationDirectory`. Pin the exact values returned by authoritative
publication. Defaults do not imply authority. Generation pins must not be
rolled back when reloading an indicator. Configuration expiry is explicit;
no new trading freshness/risk thresholds are introduced.

Bootstrap runs in `State.DataLoaded` after resolving and validating the native
account. It verifies DPAPI, fingerprint, exact HMAC/canonical encoding/schema,
all identity/generation/path pins, and expiry before configuring the owner.
Initialization is one attempt per indicator instance, including failure; retry
requires explicit configuration correction and reload. Restore reconstructs
existing state without starting the native reconciliation service. It never
consumes an activation or invokes native mutation. Persisted uncertainty and
reconciliation fences are not cleared by bootstrap. This commissioning path
does not create an execution-enabling capability even after successful setup.

## Observation

The existing V2 snapshot reader requires an exact key set, so its schema is
unchanged. `controlled-v3-commissioning-status.json` is a separate atomic file
in the configured `RuntimeSnapshotDirectory`. Its heartbeat reports validated
non-secret identity/configuration/path readiness, restore/fence status, false
safety constants and bounded error codes. Missing prerequisites report disabled
state. An absent/unwritable output directory is not successful observation.

The owner namespace remains `NinjaTrader.NinjaScript.Indicators` across all
three partials; the helper/model namespace is `Arms.NativeSim`. No test harness
is a deployment dependency. Backup must be outside the entire active Custom
tree. Replace the old non-partial owner in place, never retain a renamed `.cs`
backup there.

`tools/sim_native_deployment_gate_v3.py` requires an explicit `--phase`:

- `--phase manifest --repo <approved-checkout> --custom <Custom>` inventories the exact
  source/destination SHA256 values and COPY/REPLACE/ALREADY_CURRENT actions.
  This is `REPOSITORY_MANIFEST` / `INVENTORY_ONLY`, not destination readiness.
  Establish the approved repository commit separately; hashes derived from an
  arbitrary checkout do not prove that checkout is approved.
- `--phase pre-deployment --repo <approved-checkout> --custom <Custom> --project <csproj>`
  is `PRE_DEPLOYMENT_SOURCE_GATE`. It requires every destination to match the
  manifest SHA256 over the complete file bytes. BOM, whitespace, line endings
  and generated suffixes are never normalized or ignored. Expected and actual
  hashes remain in the report; the gate never rewrites files. It also checks
  exact destinations, all active source declarations, the three intended owner
  partials, unique helper/model declarations, absence of harnesses, both false
  constants and exactly one explicit project inclusion per source.
- `--phase post-compile` takes the same path arguments as `pre-deployment`, retains those
  checks, and always returns not-ready/nonzero with
  `MANUAL_COMMISSIONING_REQUIRED:GENERATED_SOURCE_AND_NATIVE_BUILD`. It cannot
  certify a native compile or approve generated source variants offline.

No phase is inferred from the presence of `--project`.

Read-only inspection during RC2R3 found generated Indicator, MarketAnalyzerColumn
and Strategy wrappers in installed standard indicator `Indicators/@APZ.cs`.
The installed ARMS owner had no generated suffix. These existing files establish
conventions, not deterministic output from compiling the changed ARMS source.
No NinjaTrader compile was performed. Therefore post-compile source acceptance
remains a manual commissioning gate: retain the approved pre-deployment hashes,
capture and review complete before/after source bytes and actual build evidence,
and stop on unexplained additions. A separately approved generated artifact or
proven strict validator is needed before automated post-compile certification.
Never discard everything following a generated-code marker or overwrite a
changed source merely to obtain matching hashes.

The inspected installed project has no explicit `System.Security` reference.
DPAPI's .NET Framework `ProtectedData` requires it. During separately authorized
commissioning, use NinjaScript Editor's right-click **References** dialog to add
the installed .NET Framework `System.Security.dll` (normally
`%WINDIR%\Microsoft.NET\Framework64\v4.0.30319\System.Security.dll`). This is a
framework reference, not another deployed ARMS source or a new package. Compile
and verify the resulting reference read-only with the gate. No installed
project/reference is changed during this offline task.

RC3A-R1 read-only inspection captured this actual editor-generated subtree:

```xml
<Reference Include="System.Security"><HintPath>C:\Windows\Microsoft.NET\Framework64\v4.0.30319\System.Security.dll</HintPath></Reference>
```

Its parent `ItemGroup` has no attributes; the root is `Project
Sdk="Microsoft.NET.Sdk"`. Reference, parent, root and HintPath have no Condition.
The prior blanket metadata rejection incorrectly rejected this framework path.

The gate now requires exactly one unconditional System.Security reference in a
top-level unconditional ItemGroup, with exactly one HintPath child. Missing or
empty HintPath fails; the old bare-reference positive fixtures now use the
observed editor form. All prior D3 negative cases remain enforced. No other
metadata is allowed: Aliases, Private, SpecificVersion, EmbedInteropTypes,
unknown attributes, extra children, nested nodes and conflicting or identical
duplicate references fail closed. This exception applies only to System.Security.

The approved DLL location is derived from `%WINDIR%`, under
`Microsoft.NET\Framework64\v4.0.30319\System.Security.dll`. The gate requires
that exact existing framework location and filename, rejects traversal,
relative/UNC paths and reparse redirection, and inspects the assembly using the
installed Windows PowerShell's metadata-only `AssemblyName.GetAssemblyName`.
The identity must be `System.Security, Version=4.0.0.0, Culture=neutral,
PublicKeyToken=b03f5f7f11d50a3a`. It does not load or execute the candidate assembly.
An arbitrary copy of the genuine DLL in a repository, Custom or another
directory is not approved. Missing files, unavailable metadata inspection and
identity mismatches fail closed. The file and installed project remain read-only.

Conditions are never evaluated: even literal true is outside the unconditional
contract. Conditional references/ancestors/HintPath, references inside targets
or Choose branches, and reference removal/update/exclusion operations fail.
Errors distinguish missing reference, missing HintPath, conditional context,
unapproved metadata/path, duplicates and invalid assembly identity; invalid
metadata is not mislabeled as a missing reference. Malformed/unreadable XML fails.
Native build evidence is still required; the static gate does not execute or
claim to evaluate imported MSBuild targets.

`compile_offline` compiles every production body against installed SDK metadata.
Only the installed Indicator base is accessed through the NTBase assembly
alias. The stale installed bridge is not imported globally, so CS0436 cannot
mask source duplication. CS0612/CS0436 or any compile error fail the gate.
Unreachable-code warnings from hard-disabled native submission are retained.
Both CreateOrder sites use the 12-argument overload with OrderEntry.Automated
and Core.Globals.MaxDate; collection protection submission remains unchanged.

Only after the native compile gate passes may the human re-add the indicator
with Sim101/Simulator/NQ DEC26, explicit pins/directories, one-shot OFF and
emergency OFF. Observe fresh V2/V3 heartbeats, FLAT and zero active orders.
Native OCO behavior still requires separately authorized runtime certification.
